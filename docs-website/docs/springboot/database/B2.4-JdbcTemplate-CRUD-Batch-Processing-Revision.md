**Project:** Banking System\
**Database:** PostgreSQL\
**Learning path:** Spring JDBC / Spring Boot Database Integration

## Learning objectives

By the end of this lesson, you should be able to:

-   Implement repository CRUD operations using `JdbcTemplate`.
-   Retrieve PostgreSQL-generated IDs with `KeyHolder`.
-   Map query results to Java objects using `RowMapper`.
-   Implement pagination instead of loading large tables.
-   Perform safe deposit and withdrawal updates directly in SQL.
-   Insert and update many records with `batchUpdate()`.
-   Understand batch size, transaction boundaries, and performance
    trade-offs.
-   Explain the important concepts in an interview.

## 1. Repository architecture

``` text
AccountService
     |
     v
AccountRepository
     |
     +-- JdbcTemplate
     +-- RowMapper
     +-- KeyHolder
     +-- Batch operations
     |
     v
PostgreSQL
```

`NamedParameterJdbcTemplate` is useful when SQL has named parameters
such as `:accountId`. The examples in this lesson use positional `?`
parameters, so `JdbcTemplate` is sufficient. Inject
`NamedParameterJdbcTemplate` only when the repository actually uses it.

### CRUD method map

  Operation             Typical Spring JDBC method
  --------------------- ----------------------------
  Insert                `update()`
  Select one            `queryForObject()`
  Select multiple       `query()`
  Update                `update()`
  Delete                `update()`
  Batch insert/update   `batchUpdate()`

`update()` returns the affected-row count. `query()` returns a list.
`queryForObject()` expects one result row; no row or more than one row
can result in an exception.

`account_id`, `account_holder`, `account_type`, `balance`, `status`, and

## 3. CREATE --- Insert an account and return its generated ID

PostgreSQL can generate an ID automatically using an identity column or
`BIGSERIAL`. When the application needs the new ID immediately, use
Spring JDBC's `KeyHolder` abstraction.

``` java
import java.math.BigDecimal;
import java.sql.PreparedStatement;
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;

public Long createAccount(
        String accountHolder,
        String accountType,
        BigDecimal balance,
        String status) {

    String sql = """
            INSERT INTO accounts
                (account_holder, account_type, balance, status)
            VALUES (?, ?, ?, ?)
            """;

    KeyHolder keyHolder = new GeneratedKeyHolder();

    jdbcTemplate.update(connection -> {
        PreparedStatement ps = connection.prepareStatement(
                sql,
                new String[]{"account_id"}
        );

        ps.setString(1, accountHolder);
        ps.setString(2, accountType);
        ps.setBigDecimal(3, balance);
        ps.setString(4, status);

        return ps;
    }, keyHolder);

    Number key = keyHolder.getKey();

    if (key == null) {
        throw new IllegalStateException("Account ID was not generated");
    }

    return key.longValue();
}
```

### Internal flow

``` text
Java prepares INSERT
       |
       v
PostgreSQL inserts the row and generates account_id
       |
       v
GeneratedKeyHolder receives the generated key
       |
       v
Repository returns the ID to the caller
```

Usage:

``` java
Long id = accountRepository.createAccount(
        "Supriyo",
        "SAVINGS",
        new BigDecimal("50000.00"),
        "ACTIVE"
);

System.out.println("Created account ID: " + id);
```

**Important:** `getKey()` is intended for a single generated numeric
key. It can fail if no key is returned or if the result contains
multiple keys. Request the generated column explicitly and handle a
missing key.

## 4. READ --- Fetch accounts

### Fetch one account by ID

``` java
public Account findById(Long accountId) {

    String sql = """
            SELECT account_id, account_holder, account_type,
                   balance, status, created_at
            FROM accounts
            WHERE account_id = ?
            """;

    return jdbcTemplate.queryForObject(sql, rowMapper, accountId);
}
```

`queryForObject()` is appropriate when exactly one row is expected. If
the account does not exist, Spring JDBC raises an exception (commonly
`EmptyResultDataAccessException`). Decide in the service/API layer
whether to translate that into a not-found response.

### Fetch all accounts

``` java
public List<Account> findAll() {

    String sql = """
            SELECT account_id, account_holder, account_type,
                   balance, status, created_at
            FROM accounts
            ORDER BY account_id
            """;

    return jdbcTemplate.query(sql, rowMapper);
}
```

Use `findAll()` only when the result set is known to be reasonably
small. Avoid loading an unbounded production table into application
memory.

### Basic limit/offset pagination

``` java
public List<Account> findPage(int limit, int offset) {

    String sql = """
            SELECT account_id, account_holder, account_type,
                   balance, status, created_at
            FROM accounts
            ORDER BY account_id
            LIMIT ? OFFSET ?
            """;

    return jdbcTemplate.query(sql, rowMapper, limit, offset);
}
```

Usage:

``` java
List<Account> accounts = accountRepository.findPage(20, 0);
```

This returns the first 20 rows. Validate `limit` and `offset` before
executing the query; for example, require a positive bounded limit and a
non-negative offset.

**Performance note:** Large offsets can become expensive because the
database still has to walk past skipped rows. For deep pagination,
keyset/seek pagination (for example,
`WHERE account_id > ? ORDER BY account_id LIMIT ?`) is often more
efficient. Keyset pagination requires a stable ordering key and will be
covered separately.

## 5. UPDATE --- Deposit and withdraw

### Deposit

``` java
public int deposit(Long accountId, BigDecimal amount) {

    String sql = """
            UPDATE accounts
            SET balance = balance + ?
            WHERE account_id = ?
              AND status = 'ACTIVE'
            """;

    return jdbcTemplate.update(sql, amount, accountId);
}
```

### Withdraw

``` java
public int withdraw(Long accountId, BigDecimal amount) {

    String sql = """
            UPDATE accounts
            SET balance = balance - ?
            WHERE account_id = ?
              AND status = 'ACTIVE'
              AND balance >= ?
            """;

    return jdbcTemplate.update(sql, amount, accountId, amount);
}
```

### Why the withdrawal SQL is safer

Suppose the balance is ₹1,000 and two requests each try to withdraw
₹800.

A read-check-write sequence in Java can be unsafe if both requests read
the old balance before either update is committed. Both may decide that
the withdrawal is allowed.

The conditional SQL performs the check and update as one database
statement:

``` sql
UPDATE accounts
SET balance = balance - 800
WHERE account_id = 1
  AND status = 'ACTIVE'
  AND balance >= 800;
```

PostgreSQL coordinates concurrent updates to the same row and
re-evaluates the row condition as needed. This prevents both withdrawals
from succeeding against the same ₹1,000 balance under the normal
`READ COMMITTED` behavior.

The affected-row count is meaningful:

-   `1` --- the update succeeded.
-   `0` --- no row matched; the account may not exist, may not be
    active, or may have insufficient balance.

The repository cannot distinguish those reasons from this count alone.
Add a follow-up check or a more explicit service/database design if the
API needs a precise failure reason.

**Validation still matters:** reject null, zero, or negative amounts in
the service layer, and consider database constraints such as
`CHECK (balance >= 0)`. The SQL condition is not a substitute for input
validation.

## 7. DELETE --- Delete an account

``` java
public int deleteAccount(Long accountId) {

    String sql = """
            DELETE FROM accounts
            WHERE account_id = ?
            """;

    return jdbcTemplate.update(sql, accountId);
}
```

Return value:

-   `1` --- one account deleted.
-   `0` --- no matching account.

A foreign-key reference from `transactions` may prevent deletion unless
the schema explicitly defines another referential action.

**Banking design note:** Financial accounts and their transaction
history are generally not physically deleted. Account closure or a
status change is usually safer for auditability and record retention.

## 8. Batch processing --- Insert many transactions

For a large number of inserts, repeatedly calling `update()` in a loop
creates repeated execution overhead:

``` java
for (Transaction transaction : transactions) {
    jdbcTemplate.update(sql, /* parameters */);
}
```

Use `batchUpdate()` to submit multiple parameter sets for the same SQL
statement.

### Batch insert method

``` java
public int[] batchInsertTransactions(List<Transaction> transactions) {

    String sql = """
            INSERT INTO transactions
                (account_id, transaction_type, amount, description)
            VALUES (?, ?, ?, ?)
            """;

    return jdbcTemplate.batchUpdate(
            sql,
            transactions,
            500,
            (ps, transaction) -> {
                ps.setLong(1, transaction.getAccountId());
                ps.setString(2, transaction.getTransactionType());
                ps.setBigDecimal(3, transaction.getAmount());
                ps.setString(4, transaction.getDescription());
            }
    );
}
```

This overload takes:

``` java
batchUpdate(sql, collection, batchSize, parameterSetter)
```

  -----------------------------------------------------------------------
  Argument                            Meaning
  ----------------------------------- -----------------------------------
  `sql`                               SQL statement to execute repeatedly

  `collection`                        Input records

  `batchSize`                         Number of records grouped into each
                                      batch

  `parameterSetter`                   Binds each record's values to the
                                      `PreparedStatement`
  -----------------------------------------------------------------------

A batch size of `500` is only an example, not a universal best value.
Benchmark realistic sizes such as 100, 500, and 1,000 with
representative data.

### Example usage

``` java
List<Transaction> transactions = new ArrayList<>();

for (int i = 0; i < 1000; i++) {
    transactions.add(
            new Transaction(
                    null,
                    1L,
                    "DEPOSIT",
                    new BigDecimal("100.00"),
                    LocalDateTime.now(),
                    "Bulk test transaction " + i
            )
    );
}

int[] results = accountRepository.batchInsertTransactions(transactions);

System.out.println("Batch result entries: " + results.length);
```

The returned `int[]` contains update counts or JDBC special values.
Common values include:

-   `1` --- one row affected.
-   `0` --- no rows affected.
-   `Statement.SUCCESS_NO_INFO` --- operation succeeded, but the exact
    row count is unavailable.
-   `Statement.EXECUTE_FAILED` --- a batch command failed, where
    reported by the driver.

Do not assume every driver always returns a simple `1` for every
successful batch entry.

## 9. Batch update --- Update multiple account statuses

### DTO

``` java
package com.bank.model;

public class AccountStatusUpdate {

    private final Long accountId;
    private final String status;

    public AccountStatusUpdate(Long accountId, String status) {
        this.accountId = accountId;
        this.status = status;
    }

    public Long getAccountId() {
        return accountId;
    }

    public String getStatus() {
        return status;
    }
}
```

### Repository method

``` java
public int[] batchUpdateStatus(List<AccountStatusUpdate> updates) {

    String sql = """
            UPDATE accounts
            SET status = ?
            WHERE account_id = ?
            """;

    return jdbcTemplate.batchUpdate(
            sql,
            updates,
            200,
            (ps, update) -> {
                ps.setString(1, update.getStatus());
                ps.setLong(2, update.getAccountId());
            }
    );
}
```

Usage:

``` java
List<AccountStatusUpdate> updates = List.of(
        new AccountStatusUpdate(1L, "BLOCKED"),
        new AccountStatusUpdate(2L, "BLOCKED"),
        new AccountStatusUpdate(3L, "ACTIVE")
);

int[] results = accountRepository.batchUpdateStatus(updates);
```

Typical use cases:

-   Bulk status changes.
-   Data imports.
-   Scheduled maintenance.
-   Migration jobs.
-   Bulk transaction insertion.

Validate IDs and allowed status values before executing the batch.

## 10. Batch performance --- What actually improves?

For 5,000 inserts, a batch size of 500 means the application groups the
work into 10 batches at the Spring API level.

``` text
Individual execution:
Application -> execute insert 1
            -> execute insert 2
            -> execute insert 3
            -> ...
            -> execute insert 5000

Batch execution:
Application -> batch of parameter sets
            -> batch of parameter sets
            -> ...
            -> database
```

Potential benefits:

-   Less repeated communication overhead.
-   Less repeated statement execution overhead.
-   Improved throughput for suitable bulk workloads.

**Important:** A JDBC batch does not guarantee exactly one network round
trip per batch. Actual behavior depends on Spring, the JDBC driver,
connection settings, database, and workload. Benchmark rather than
assuming a fixed speed-up.

### PostgreSQL JDBC driver option

The PostgreSQL JDBC driver supports a batch insert rewrite option:

``` properties
spring.datasource.url=jdbc:postgresql://localhost:5432/banking_db?reWriteBatchedInserts=true
```

This can let the driver rewrite eligible batched inserts into more
efficient SQL forms. Test it with the actual PostgreSQL JDBC driver
version, schema, generated-key requirements, and workload. Do not assume
it improves every batch operation.

## 11. Production considerations

### 11.1 A batch is not automatically all-or-nothing

Batch execution and transaction atomicity are different concerns. If all
records in an import must succeed or fail together, execute the batch
inside a Spring-managed transaction.

Prefer placing the transaction boundary in the service layer:

``` java
@Service
public class TransactionImportService {

    private final AccountRepository accountRepository;

    public TransactionImportService(AccountRepository accountRepository) {
        this.accountRepository = accountRepository;
    }

    @Transactional
    public void importTransactions(List<Transaction> transactions) {
        accountRepository.batchInsertTransactions(transactions);
    }
}
```

With Spring's default proxy-based transaction management, the method
should be invoked through the Spring-managed bean proxy. A call from one
method to another method on the same instance
(`this.someTransactionalMethod()`) does not normally activate
proxy-based transaction interception.

By default, Spring rolls back on unchecked exceptions
(`RuntimeException` and `Error`). Checked exceptions do not trigger
rollback by default; configure `rollbackFor` when required. Ensure the
exception is not swallowed inside the transactional method.

### 11.2 Avoid loading huge datasets

Avoid unbounded reads such as:

``` java
List<Account> all = accountRepository.findAll();
```

Consider:

-   Limit/offset pagination for straightforward page-based navigation.
-   Keyset pagination for deep sequential navigation.
-   JDBC fetch size for suitable large-result processing.
-   Bounded batch processing for bulk writes.
-   Streaming-oriented processing where appropriate.

Fetch size is a driver hint, not a guarantee that the entire result will
never be buffered. PostgreSQL cursor-based fetching also has transaction
and connection requirements; configure and test it deliberately.

### 11.3 Validate before batch operations

Validate:

-   Account ID and referenced account existence, where required.
-   Positive transaction amount.
-   Allowed transaction type and account status.
-   Required fields and maximum field lengths.
-   Duplicate/idempotency keys.
-   Batch size and request size.

Never allow an unbounded client request to create an arbitrarily large
in-memory batch.

### 11.4 Additional performance habits

-   Select only the columns needed; avoid unnecessary `SELECT *`.
-   Index columns used frequently in `WHERE`, join, and ordering
    clauses, based on query plans.
-   Reuse parameterized SQL rather than constructing SQL with user
    input.
-   Measure query plans and execution time before optimizing.
-   Keep transactions appropriately scoped; very large transactions can
    hold locks and consume resources for too long.

## 12. Consolidated repository --- Lesson implementation

The following is the consolidated set of repository methods from this
lesson. It assumes the `Account`, `Transaction`, and
`AccountStatusUpdate` model classes and `AccountRowMapper` already
exist.

``` java
package com.bank.repository;

import com.bank.mapper.AccountRowMapper;
import com.bank.model.Account;
import com.bank.model.Transaction;
import com.bank.model.AccountStatusUpdate;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.support.GeneratedKeyHolder;
import org.springframework.jdbc.support.KeyHolder;
import org.springframework.stereotype.Repository;

import java.math.BigDecimal;
import java.sql.PreparedStatement;
import java.util.List;

@Repository
public class AccountRepository {

    private final JdbcTemplate jdbcTemplate;
    private final AccountRowMapper rowMapper = new AccountRowMapper();

    public AccountRepository(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    // CREATE: insert account and return generated ID
    public Long createAccount(
            String holder,
            String type,
            BigDecimal balance,
            String status) {

        String sql = """
                INSERT INTO accounts
                    (account_holder, account_type, balance, status)
                VALUES (?, ?, ?, ?)
                """;

        KeyHolder keyHolder = new GeneratedKeyHolder();

        jdbcTemplate.update(connection -> {
            PreparedStatement ps = connection.prepareStatement(
                    sql,
                    new String[]{"account_id"}
            );

            ps.setString(1, holder);
            ps.setString(2, type);
            ps.setBigDecimal(3, balance);
            ps.setString(4, status);

            return ps;
        }, keyHolder);

        Number key = keyHolder.getKey();

        if (key == null) {
            throw new IllegalStateException("Account ID was not generated");
        }

        return key.longValue();
    }

    // READ ONE
    public Account findById(Long accountId) {

        String sql = """
                SELECT account_id, account_holder, account_type,
                       balance, status, created_at
                FROM accounts
                WHERE account_id = ?
                """;

        return jdbcTemplate.queryForObject(sql, rowMapper, accountId);
    }

    // READ ALL
    public List<Account> findAll() {

        String sql = """
                SELECT account_id, account_holder, account_type,
                       balance, status, created_at
                FROM accounts
                ORDER BY account_id
                """;

        return jdbcTemplate.query(sql, rowMapper);
    }

    // PAGINATION
    public List<Account> findPage(int limit, int offset) {

                SELECT account_id, account_holder, account_type,
                       balance, status, created_at
                FROM accounts
                ORDER BY account_id

    }

    // DEPOSIT
    public int deposit(Long accountId, BigDecimal amount) {

        String sql = """
                UPDATE accounts
                SET balance = balance + ?
                WHERE account_id = ?

                """;

    public int withdraw(Long accountId, BigDecimal amount) {

                UPDATE accounts
                SET balance = balance - ?
                WHERE account_id = ?
                  AND status = 'ACTIVE'
                  AND balance >= ?
                """;

        return jdbcTemplate.update(sql, amount, accountId, amount);
    }

    // UPDATE DETAILS
    public int updateAccountDetails(
            Long accountId,
            String holder,
            String type) {

        String sql = """
                UPDATE accounts
                SET account_holder = ?,
                    account_type = ?
                WHERE account_id = ?
                """;

        return jdbcTemplate.update(sql, holder, type, accountId);
    }

    // UPDATE STATUS
    public int updateStatus(Long accountId, String status) {

        String sql = """
                UPDATE accounts
                SET status = ?
                WHERE account_id = ?
                """;

        return jdbcTemplate.update(sql, status, accountId);
    }

    // DELETE
    public int deleteAccount(Long accountId) {

        String sql = """
                DELETE FROM accounts
                WHERE account_id = ?
                """;

        return jdbcTemplate.update(sql, accountId);
    }

    // BATCH INSERT TRANSACTIONS
    public int[] batchInsertTransactions(List<Transaction> transactions) {

        String sql = """
                INSERT INTO transactions
                    (account_id, transaction_type, amount, description)
                VALUES (?, ?, ?, ?)
                """;

        return jdbcTemplate.batchUpdate(
                sql,
                transactions,
                500,
                (ps, transaction) -> {
                    ps.setLong(1, transaction.getAccountId());
                    ps.setString(2, transaction.getTransactionType());
                    ps.setBigDecimal(3, transaction.getAmount());
                    ps.setString(4, transaction.getDescription());
                }
        );
    }

    // BATCH UPDATE ACCOUNT STATUS
    public int[] batchUpdateStatus(List<AccountStatusUpdate> updates) {

        String sql = """
                UPDATE accounts
                SET status = ?
                WHERE account_id = ?
                """;

        return jdbcTemplate.batchUpdate(
                sql,
                updates,

}
```

**Implementation note:** The repository above is a teaching baseline. In
a production banking application, add service-layer validation,
authorization, transaction boundaries, idempotency controls, audit
logging, and domain-specific error handling. In particular, a real money
transfer must debit and credit accounts within one transaction and must
address concurrency and duplicate-request handling.

## 13. Interview preparation

### Q1. What is `KeyHolder`?

`KeyHolder` is a Spring JDBC abstraction that stores generated keys
returned by an insert operation. `GeneratedKeyHolder` is a common
implementation.

### Q2. Why use batch processing?

It groups repeated operations and can reduce communication and
statement-execution overhead, improving throughput for bulk workloads.

### Q3. Does `batchUpdate()` guarantee atomicity?

No. Atomicity depends on transaction boundaries and database/driver
behavior. Use a Spring-managed transaction when all-or-nothing behavior
is required.

### Q4. Does batch size 1,000 always perform better than 100?

No. Larger batches may improve throughput but can increase memory use,
transaction duration, lock duration, and the impact of failures.
Benchmark realistic workloads.

### Q5. What does `batchUpdate()` return?

An `int[]` of update counts or JDBC special result values such as
`SUCCESS_NO_INFO` or `EXECUTE_FAILED`, depending on driver behavior.

### Q6. How do you retrieve an auto-generated ID after an insert?

Create a `GeneratedKeyHolder`, request the generated column when
preparing the statement, pass the holder to `JdbcTemplate.update()`, and
read the generated key.

### Q7. Why is pagination necessary?

It limits the rows transferred and held in application memory for a
request. Keyset pagination can be more efficient than large offsets for
deep sequential navigation.

### Q8. Why is a conditional withdrawal update safer than checking the balance in Java first?

The balance condition and subtraction occur in one database statement.
This avoids the race where concurrent requests both validate the same
stale balance in application code.

### Q9. Should a banking account be physically deleted?

Usually not. Account closure/status changes and retention of transaction
history are generally safer for auditability and financial records.

### CRUD method map

  -----------------------------------------------------------------------
  Task                    Method / concept        Remember
  ----------------------- ----------------------- -----------------------
  Insert and return ID    `update()` +            Request generated
                          `GeneratedKeyHolder`    column

  Read one                `queryForObject()`      Expects exactly one row

  Read many               `query()`               Returns `List<T>`

  Update                  `update()`              Check affected-row
                                                  count

  Delete                  `update()`              Foreign keys may
                                                  prevent deletion

  Batch writes            `batchUpdate()`         Returns `int[]`
  -----------------------------------------------------------------------

### Batch processing

``` text
Collection of records
        |
        v
JdbcTemplate.batchUpdate()
        |
        +-- SQL statement
        +-- batch size
        +-- parameter setter
        |
        v
JDBC driver / PostgreSQL
```

Remember:

-   Batch processing reduces repeated execution overhead; it does not
    automatically guarantee atomicity.
-   Use `@Transactional` when the batch must be all-or-nothing.
-   Choose batch size through measurement, not guesswork.
-   Validate inputs and bound the maximum batch size.
-   Driver update counts may include special values.

### Performance and production checklist

-   [ ] Avoid unbounded `findAll()` for large tables.
-   [ ] Use pagination; consider keyset pagination for deep pages.
-   [ ] Select only required columns.
-   [ ] Add indexes based on actual query patterns and query plans.
-   [ ] Benchmark batch sizes with realistic data.
-   [ ] Test PostgreSQL `reWriteBatchedInserts` before relying on it.
-   [ ] Keep transactions appropriately scoped.
-   [ ] Validate positive monetary amounts and allowed statuses.
-   [ ] Use database constraints as a final integrity safeguard.
-   [ ] Preserve banking account and transaction audit history.

### Five facts to memorize

1.  `JdbcTemplate.update()` is used for inserts, updates, and deletes.
2.  `queryForObject()` reads one expected row; `query()` reads multiple
    rows.
3.  `GeneratedKeyHolder` retrieves database-generated keys.
4.  `batchUpdate()` groups repeated statements and returns update
    results.
5.  `@Transactional` provides the transaction boundary; batching alone
    does not.
